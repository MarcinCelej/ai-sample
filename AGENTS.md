# AGENTS.md

Instructions for AI coding agents working in this repository. Humans should read them too.

## Project

ClassBook (working name) lets an organization publish courses and classes and lets families enroll in them; payments are settled by importing bank statements. See [README.md](README.md) for features and tech stack.

- Backend: ASP.NET Core Web API (.NET 10), SQL Server, Entity Framework Core
- Frontend: React + TypeScript, Tailwind CSS, shadcn/ui
- CI: GitHub Actions
- UI language is Polish, built for internationalization. A single organization at start; the architecture must be ready for multi-tenancy.

The binding engineering rules (structure, naming, patterns, testing) are in [.ai/specs/2026-10-25-engineering-standards.md](.ai/specs/2026-10-25-engineering-standards.md). Read it before changing code. The reference slice to copy for new features is `backend/src/Modules/ClassBook.Modules.Courses` (`CreateCourse`, `GetCourses`) with `frontend/src/features/courses`.

## Repository structure

```

  src/ClassBook.Api/       Thin host (Program.cs)
  src/ClassBook.Shared/    Cross-cutting building blocks; references no module
  src/Modules/             One project per module: Identity, Courses, Families, Enrollments, Payments

  src/api/generated/       Generated by Orval – never edit by hand

```

## Commands

Run backend commands from `backend/` and frontend commands from `frontend/`.

| Task | Command |
|---|---|
| Restore tools (once) | `dotnet tool restore` |
| Dev database connection (once) | `dotnet user-secrets set ConnectionStrings:ClassBook "<connection string>" --project src/ClassBook.Api` |
| Build (also regenerates `openapi/v1.json`) | `dotnet build` |
| Run the API (https://localhost:7108, migrates in Development) | `dotnet run --project src/ClassBook.Api` |
| Backend unit + architecture tests | `dotnet test --project tests/ClassBook.UnitTests` and `dotnet test --project tests/ClassBook.ArchitectureTests` |
| Backend integration tests (need Docker) | `dotnet test --project tests/ClassBook.IntegrationTests` |
| Backend tests with coverage (Cobertura in `TestResults/`) | `dotnet test --coverlet --coverlet-output-format cobertura --coverlet-exclude-by-file "**/Migrations/*.cs"` |
| Format check | `dotnet format --verify-no-changes` |
| Add a migration | `dotnet ef migrations add <Name> --project src/Modules/ClassBook.Modules.<Module> --startup-project src/ClassBook.Api --context <Module>DbContext --output-dir Persistence/Migrations` |
| Review a migration's SQL | `dotnet ef migrations script --project src/Modules/ClassBook.Modules.<Module> --startup-project src/ClassBook.Api --context <Module>DbContext` |
| Install frontend packages | `npm ci` |
| Run the SPA (proxies `/api` to the API) | `npm run dev` |
| Regenerate the API client (after `dotnet build`) | `npm run api:generate` |
| Lint, type-check, test, build | `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` |
| Frontend coverage | `npm run test:coverage` |
| Format | `npm run format` (check: `npm run format:check`) |
| E2E (API and SPA running) | `npm run e2e` (first time: `npx playwright install chromium`) |

Never put connection strings or secrets in the repository.

## Rules

1. **English only.** All repository content – code, comments, docs, specs, issues, PRs, commit messages – is in English. (The user-facing UI text is Polish via localization resources.)
2. **Feature branches.** Work on a feature branch, never directly on `main`. If on `main`, create a branch first.
3. **No commit, push or merge without explicit human approval.** Ask first, every time. Approval for one commit does not carry over to the next.
4. **Everything is linked to a GitHub issue.** No work without an issue – if there is none, create it first (`gh issue create`).
   - Branch: `<type>/<issue>-<slug>`, e.g. `feat/12-waiting-list`, `fix/31-mt940-import`. Types: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`.
   - Commit: every commit subject starts with the issue reference: `[#12] Add waiting list promotion`.
   - Pull request: title starts with `[#12]`, body contains `Closes #12`. PRs are merged with a merge commit (no squash, no rebase), so every commit stays in history.
5. **Meaningful commits.** Each commit is one logical step with a clear subject and a body explaining what and why. Before opening or updating a PR, clean up the branch history (squash "wip", "fix lint", "try again" commits into the step they belong to). Rewriting history is allowed only on your own feature branch, never on `main`.

## Working method

1. **Plan complex tasks first.** For anything non-trivial (multiple files, new behavior, unclear approach), plan before editing – use plan mode where available – and base the plan on the spec. If the work goes sideways, stop and re-plan instead of pushing through.
2. **Verify every change.** Never report work as done without evidence: build, run the relevant tests, and exercise the changed behavior. Add or update tests with the change. Report failures and skipped checks plainly.
3. **Challenge your own work.** Before handing off, review the diff critically. If a fix feels like a workaround, discard it and implement the proper solution.
4. **Fix bugs from the evidence.** Start from the bug report, failing test or CI log; reproduce it with a failing test first, then fix the root cause.
5. **Keep the main context clean.** Delegate research, exploration and independent subtasks to subagents. Parallel sessions must each use their own git worktree and feature branch.

## The `.ai` folder

All agent-related working material lives in `.ai/`:

```
.ai/
├── specs/                 Specifications for spec-driven development
│   ├── YYYY-MM-DD-slug.md   Active specs (to be implemented / in progress)
│   ├── implemented/         Specs whose implementation is done
│   └── archive/             Obsolete, rejected or superseded specs
├── runs/                  Logs of autonomous AI runs
│   └── YYYY-MM-DD-slug.md
├── lessons.md             Index of lessons learned (long-term memory)
└── lessons/               Detailed lesson notes
    └── YYYY-MM-DD-slug.md
```

File names are `YYYY-MM-DD-slug.md` (date of creation, lowercase kebab-case slug).

### Specs (`.ai/specs/`)

- Development is spec-driven: for any non-trivial feature or change, there must be a spec before implementation. If none exists, write one and get human confirmation first.
- A spec states the goal, scope and non-goals, behavior/requirements, acceptance criteria and open questions.
- Implement against the spec. If reality diverges, update the spec in the same change.
- When implementation is complete, move the spec to `.ai/specs/implemented/`. Move obsolete or rejected specs to `.ai/specs/archive/`. Do not delete specs.

### Runs (`.ai/runs/`)

- Every autonomous run (work done without step-by-step human guidance) must produce a log file.
- Log: the task and linked spec, branch, decisions and assumptions, steps taken, files changed, commands/tests run with results, problems, and open items for the human.
- Create the log at the start of the run and keep it updated; do not reconstruct it afterwards.

### Lessons (`.ai/lessons.md` and `.ai/lessons/`)

- **Before starting work, read `.ai/lessons.md`** and any linked lessons relevant to the task.
- After fixing a bug, hitting a pitfall, or finding an improvement (code, process, tooling, docs), record it: add a note in `.ai/lessons/YYYY-MM-DD-slug.md` and a one-line entry in `.ai/lessons.md`. See that file for the format.
- **After every correction from the human** (review comment, rejected approach, "don't do X"), record a lesson that prevents the same mistake. If it is a durable project rule, also add it to this file.
- Keep lessons concrete and actionable. Update or remove lessons that turn out to be wrong.

## Enforcement checklist

Before finishing any task, confirm:

- [ ] A spec exists in `.ai/specs/` for the work (or the change is trivial) and is moved to `implemented/` if complete.
- [ ] An autonomous run has a log in `.ai/runs/`.
- [ ] Complex work was planned first, and the change is verified (build and tests run, results reported).
- [ ] New lessons are recorded in `.ai/lessons/` and indexed in `.ai/lessons.md`.
- [ ] All content is in English and file names follow `YYYY-MM-DD-slug.md`.
- [ ] Work is on a feature branch, and nothing was committed, pushed or merged without explicit approval.
- [ ] Branch, every commit and the PR reference the GitHub issue (`[#N]`, `Closes #N`).
